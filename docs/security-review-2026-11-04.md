## 발견 사항

### 1. 높음: 비로그인 투표의 식별자를 재발급받아 반응 수 조작 가능

- 위치: `src/app/api/community/route.ts:14`, `src/server/anonymous-votes.ts:23`, `supabase/migrations/20260917100000_anonymous_place_votes.sql:35`.
- 비로그인 요청은 쿠키 토큰의 해시로만 중복을 구분한다. 쿠키가 없으면 새 토큰을 발급하고, 이미 존재하는 값도 형식만 검사한다. 해당 API와 SQL에는 요청 빈도나 신규 식별자 발급을 제한하는 장치가 없다. 로그인 사용자의 `private.rate_limit` 경로를 거치지 않는다.
- 공격자는 동일 출처 Origin 헤더를 붙인 직접 HTTP 요청에서 쿠키를 버리거나 교체해 여러 식별자를 만들 수 있다. Origin 검증은 브라우저의 교차 출처 요청 방어이며, 봇의 신원을 검증하지 않는다.
- 로컬 재현: 같은 공개 장소에 서로 다른 해시로 150회 투표했으며 모두 허용되어 행이 150개 증가했다. 로컬 테스트 DB 트랜잭션을 롤백했다. 실제 HTTP 대량 요청이나 운영 DB 쓰기는 수행하지 않았다. API가 새 쿠키를 발급하는 경로는 코드로 확인했다.
- 영향: 장소의 찬반 수와 인기 판단을 왜곡하고 DB 쓰기·공개 캐시 무효화를 반복할 수 있다. 권한 상승 문제가 아니라 익명 참여 기능의 남용 방지 결함이다. 외부 WAF의 별도 방어 유무는 확인하지 않았다.
- 권장: 서버에서 검증된 요청 출처 정보를 이용하는 공유 저장소 기반 빈도 제한, 신규 익명 식별자 발급 제한, 의심 트래픽의 추가 검증을 함께 적용한다. 쿠키 하나당 제한만으로는 해결되지 않는다. 익명 투표를 표시 집계에서 어떻게 취급할지도 결정한다.

### 2. 중간: JSON 요청 크기 제한이 메모리 할당 이후에 실행됨

- 위치: `src/server/http.ts:51`.
- `request.text()`로 본문을 끝까지 읽은 뒤 문자열 길이를 검사한다. 따라서 12,000자 제한은 실제 수신 바이트나 메모리 사용량을 제한하지 않는다. `/api/community`는 로그인 확인 전 이 함수를 호출하므로 비로그인 직접 요청으로도 이 경로에 도달한다.
- 로컬 재현: 12,000 제한에 1MiB 스트림을 전달하자 전체 1,048,576바이트를 소비한 뒤 413을 반환했고 스트림 취소는 실행하지 않았다. 이 동작을 검증하는 테스트가 통과했다.
- 영향: 큰 본문·동시 요청에 따른 메모리와 처리 시간 낭비. 실제 상한은 호스팅 플랫폼의 요청 크기 제한에도 좌우된다. 이번 점검에서 서비스 중단 자체를 재현한 것은 아니다.
- 권장: 업로드 API처럼 스트림을 읽으며 바이트 수를 누적하고 한도 초과 시 즉시 취소한다. Content-Length 사전 검사만으로 대체하지 말고 청크 전송에도 적용한다. JSON 파싱은 제한된 본문에만 수행한다.

- 로컬 재현: 동일한 문자열 길이의 ASCII 비밀번호와 한글 입력으로 비교 함수가 예외를 던지는 것을 확인했다. 실제 관리자 비밀번호는 사용하거나 출력하지 않았다.
