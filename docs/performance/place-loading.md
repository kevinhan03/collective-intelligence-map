# 장소 조회·썸네일 배치 성능 개선

## 장소 조회

`map_places_in_bounds`의 공개 여부·좌표 조건·ID순 501개 제한을 먼저 계산한다. 각 반환 장소의 `private.place_stats`를 LATERAL/OFFSET 0으로 한 번만 계산한다. 기존 응답 구조와 익명 투표 포함 통계를 유지한다.

재현: 격리된 `*_test` DB에 전체 마이그레이션을 적용한 후 `TEST_DATABASE_URL=… node scripts/test-place-loading-db.mjs`. 스크립트는 한 트랜잭션 안에서 합성 74/500개 장소를 구성하고 원본/변경 SQL을 번갈아 적용해 각각 워밍업 2회, 측정 10회 후 모두 롤백한다. 운영 데이터를 변경하지 않는다.

첫 측정(로컬 PostgreSQL/PostGIS, 2026-11-05):

| 장소 수 | 변경 전 DB 실행 중앙값 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 74 | 43.765ms | 26.619ms | 39.2% |
| 500 | 219.775ms | 99.271ms | 54.8% |

`artifacts/performance/place-loading/`에 원본 함수 정의·전후 실행 계획과 표본을 저장한다. DB 실행 시간은 EXPLAIN ANALYZE, 클라이언트 시간은 로컬 TCP 요청부터 JSON 수신까지 별도로 측정한다. 이는 합성 데이터에서의 결과이며 실제 74곳 운영 지도나 전체 화면 로딩의 개선율이 아니다.

복구 SQL: `docs/sql/rollback-map-place-reads.sql`. 함수 시그니처·권한은 변경하지 않는다.

## 운영 DB 읽기 전용 비교

운영 DB 함수는 바꾸지 않고 원본 SELECT와 변경 SELECT를 `BEGIN READ ONLY` 안에서 anon 역할로 번갈아 실행했다. 실제 `korea-fashion-store` 지도 74곳의 JSON 응답은 일치했다. 워밍업 2회 뒤 각 10회 측정한 DB 실행 중앙값은 **200.960ms → 83.388ms (58.5% 감소)**였다. `scripts/benchmark-place-loading-live.mjs`가 EXPLAIN ANALYZE 시간과 네트워크 포함 요청 시간을 분리해 기록한다. EXPLAIN 요청의 클라이언트 시간에는 실행 계획 직렬화·전송도 포함되므로 일반 API 시간으로 해석하지 않는다.

## 썸네일 배치

- `POST /api/places/photos/previews`는 `{ placeIds: UUID[] }` 1~50개를 받고 `{ previews: { [placeId]: photoId | null } }`를 반환한다. 원래 요청 길이 제한 후 중복을 제거한다. 사진 없는 장소와 비공개 장소를 구분해 노출하지 않는다.
- 새 `place_photo_previews(uuid[])`는 invoker 권한으로 공개 장소의 visible 사진만 선택한다. 최신 created_at, 같은 시각에는 ID 내림차순을 적용한다. 기존 부분 인덱스를 사용하며 새 인덱스·테이블은 만들지 않는다.
- 목록 큐는 16ms 안에 모인 요청을 50개씩, 동시에 최대 두 배치로 처리한다. 개별 구독 취소가 다른 장소 요청을 취소하지 않는다. 목록 종료 시 모든 요청을 중단한다. 실패·누락 항목은 사진 없이 표시한다.
- 이미지 다운로드 경로, 바이트 캐시와 공개 여부 재확인, ETag/304 처리는 변경하지 않는다. 사진 업로드·숨김·삭제 직후에도 원래 다운로드 API가 공개 여부를 검사한다.

## 브라우저 측정

`npm run build` 후 `node scripts/benchmark-thumbnail-browser.mjs`. 동일 MobilePlaceList 컴포넌트에 기존 main 큐와 변경 큐를 각각 빌드하고 Chromium 390×844에서 3회씩 번갈아 실행한다. 메타데이터 응답 120ms, 이미지 응답 40ms로 고정한 합성 네트워크다. 서버 컴파일과 번들 빌드는 측정에서 제외한다.

| 시나리오 | 기존 | 변경 |
| --- | ---: | ---: |
| 첫 화면/인접 영역 7곳 메타데이터 요청 | 7회 | 1회 |
| 첫 화면/인접 영역 사진 전체 표시 중앙값 | 460ms | 231ms |
| 10곳 고정 시나리오 메타데이터 요청 | 10회 | 1회 |
| 10곳 사진 전체 표시 중앙값 | 572ms | 221ms |
| 10곳 이미지 다운로드 | 10회 | 10회 |

10곳 시나리오는 IntersectionObserver를 즉시 진입하도록 고정해 요청 수를 검증한다. 실제 초기 화면 시나리오는 원래 observer를 사용한다. 첫 사진은 배치 대기 때문에 중앙값 202ms → 220ms로 소폭 늦었다. 전체 사진 완료는 빨라지지만 첫 사진 지연이 항상 줄어드는 것은 아니다. 운영 사용자의 실제 네트워크 개선율로 해석하지 않는다.

## 검증·반영·복구

- 단위 224개 통과. 모바일 목록 E2E 5개(320/390/768px, 실패·취소·404 이미지) 통과. 타입 검사·프로덕션 빌드 통과. 전체 린트는 오류 0, 기존 prototype 파일 경고 2개다.
- 격리된 cim_perf_test DB에 전체 마이그레이션·시드와 기존 DB 회귀 테스트를 실행했다. 추가 테스트는 사진 선택·중복·범위 제한·숨김·삭제·비공개 부모·업로더/관리자 비공개 차단을 검사한다. 공개 SECURITY DEFINER 함수를 추가하지 않았다. 로컬 DB advisors는 경고/오류 없음.
- 운영 반영은 `node --env-file=.env.local scripts/rollout-place-loading.mjs --project-ref=<대상 프로젝트>`로 먼저 대상·대기 마이그레이션을 확인하고 `--apply`를 붙여 실행한다. API 주소·DB 사용자·명시한 프로젝트가 일치해야 한다. 이번 두 마이그레이션만 트랜잭션으로 적용하고 이력을 기록한다. 운영 시드·테이블 데이터는 변경하지 않는다.
- DB를 먼저 적용한 뒤 기존 앱의 지도 조회와 새 공개 RPC를 검증하고 앱을 반영한다. DB 변경은 이전 앱과 호환되므로 앱 롤백 시 유지할 수 있다. 원본 함수 정의는 적용 전에 artifacts의 rollout 디렉터리에 저장한다. DB 자체를 되돌릴 때는 그 정의를 복구하고 해당 최적화 마이그레이션 이력을 제거한다. 새 RPC를 제거할 때는 새 앱을 먼저 되돌린 후 `drop function public.place_photo_previews(uuid[])`와 해당 마이그레이션 이력만 제거한다.

운영 DB 반영 확인: 두 마이그레이션 적용 및 이력 기록 완료. 기존 bbox RPC가 74곳을 반환하고, 공개 preview RPC 10곳 결과가 기존 목록과 일치함을 확인했다. 프로덕션 모드 로컬 API에서도 no-store 응답을 확인했다. 공개 이미지 다운로드 200을 확인했다. 운영에는 기존 hidden/deleted 사진이 없어 실제 사진 상태를 변경하지 않고 해당 시나리오는 격리 DB와 회귀 테스트로 검증했다. 운영 DB advisors는 적용 후에도 경고/오류 없음.
