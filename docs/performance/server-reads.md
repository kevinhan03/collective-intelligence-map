# 서버 공개 조회 성능 점검

2026-11-05. 현재 `.env.local`의 Supabase를 읽기 전용으로 조회했다. 운영 데이터 변경이나 배포는 하지 않았다.

## 확인한 병목과 수정

- 홈 지도 목록은 지도·통계 조회가 끝난 후 홈 편집 설정을 조회했다. 설정도 처음부터 병렬로 요청한다.
- 지도 상세는 지도 행을 읽은 후 통계 → 작성자 → 편집 설정 → 태그를 순차 조회했다. 지도 행 이후 독립적인 조회를 병렬화했다. 인증·RLS·응답 구조는 유지한다.
- Hype 하나를 변경해도 `public-community` 전체 캐시가 즉시 만료됐다. Hype은 `map-engagement` 태그로 목록의 순위 통계만 만료시킨다. 지도 목록은 두 태그를 모두 유지하므로 기존 공개 데이터 변경의 무효화도 계속 작동한다. 저장·제안·검수 등 다른 변경은 기존 무효화를 유지한다.
- 홈 지역 검색 캐시의 인자에는 지도 통계·편집 설정 전체가 들어갔다. 지역에 영향을 주는 정렬·중복 제거된 지도 ID만 키에 포함시켜 Hype 통계 변경 후에도 같은 지역 캐시를 재사용한다.

## 측정

로컬 Node에서 원격 Supabase 공개 API를 호출했다. 첫 묶음의 네 요청은 각각 약 1,446~1,525ms, 연결 이후에는 약 53~162ms였다. 첫 연결 수치에는 DNS/TLS·네트워크·원격 준비 시간이 함께 포함되며 서버 콜드 스타트로 단정하지 않는다.

같은 공개 지도에 대해 지도 행·통계·편집 설정·태그를 조회했다. 변경 전 순차 방식과 변경 후 병렬 방식을 번갈아 실행했다. 모든 응답은 성공했다.

| 반복 | 순차 | 병렬 |
| --- | ---: | ---: |
| 1 | 254ms | 168ms |
| 2 | 135ms | 105ms |
| 3 | 278ms | 81ms |
| 중앙값 | 254ms | 105ms |

이 표는 DB 요청 구간만 측정한다. 실제 Next.js 요청, 캐시 적중, 브라우저 렌더링, 지도 SDK·사진 다운로드를 포함하지 않아 전체 서비스가 59% 빨라졌다는 의미는 아니다. 소수 반복이며 네트워크 변동도 포함된다.

홈 지역 목록은 202개 행, 1페이지, 약 145ms였다. 현재 데이터에서는 큰 병목이 아니지만 데이터가 늘면 500행씩 순차 조회하므로 DB에서 지도별 지역을 집계하는 RPC로 대체할 후보이다.

## 다음 우선순위

1. 실제 서비스 URL에서 비로그인·로그인 상태별 TTFB, API 응답 시간, LCP를 측정한다. 로컬 환경의 사이트 URL은 localhost이고 이번 점검 중 실행 중인 앱 서버를 찾지 못했으므로 운영 화면의 체감 지연 원인은 확정하지 않았다.
2. 배포 함수와 DB의 리전을 확인한다. 리전 간 지연은 모든 DB 왕복에 누적된다. 이번 수정은 배포 설정을 변경하지 않았다.
3. `public-community`를 지도·장소·댓글 단위로 더 분리한다. 현재 Hype 외의 쓰기는 전체 캐시를 만료시키므로 트래픽이 늘면 반복 재조회가 발생할 수 있다. 제안·검수·병합·삭제가 영향을 주는 데이터를 빠짐없이 무효화하도록 정합성 검증과 함께 진행해야 한다.
4. 캐시가 없는 로그인 요청의 `getUser` 및 프로필·역할 조회와 장소 사진·지도 스타일 요청을 각각 계측한다. 인증 검증을 생략하는 방식으로 최적화하지 않는다.

## 검증

- 지연된 통계 조회 중에도 작성자·편집 설정·태그가 시작되는지 회귀 테스트한다.
- 목록 조회 중에도 편집 설정 요청이 시작되는지 회귀 테스트한다.
- Hype 성공 시 순위 태그 무효화, 실패 시 무효화하지 않음을 테스트한다.
- 전체 단위 테스트: 63개 파일, 219개 테스트 통과.
- 타입 검사, 수정 파일 ESLint, 프로덕션 빌드 통과.
